# Phase 1A: what the 4.0.13 backport actually costs -- 2026-09-07

Measured, not estimated. Both halves were really compiled against the real install at `C:\SPT`.
Every claim below survived an adversarial re-check; where the re-check overturned something, the
correction is what is written down.

## The client half: two renames. That is the whole thing.

The work order called the client the "real unknown" -- 4.1.0 shipped a deobfuscated client and
4.0.13's is the older obfuscated one, so the fear was that Harmony patches and type references
simply would not resolve. **They do.**

An unmodified build of `src/Casino.Client/Casino.Client.csproj` against `-p:SPTPath=C:\SPT`
produces **exactly three errors, all CS0246, all in one file**, naming two types:

| `src/SlotMachine.Client/ItemArt.cs:310,315` | 4.0.13 name |
| --- | --- |
| `ItemFactory` | `ItemFactoryClass` |
| `ItemIconCreator` | `GClass926` |

Both were found by dumping all 15,137 `TypeDef`s out of `Assembly-CSharp.dll`, and `GClass926` was
confirmed by disassembling `ItemViewFactory.GetItemSpriteAsync` -- the game's own code resolves the
icon renderer as `Singleton<GClass926>`, so the mod's guard checks precisely the right object.
After the two renames: **0 errors, 0 warnings, reproducible from a wiped `bin`/`obj`.**

Why it was so cheap: the built plugin references only **19 `Assembly-CSharp` types, and 17 kept
their names**. Only `GClass846` and `GClass926` carry obfuscation-generated names at all.

The `net472` targeting pack was not a problem either -- NuGet auto-restored
`Microsoft.NETFramework.ReferenceAssemblies.net472` during the build, so the 8.0 SDK already on
PATH is enough. **No .NET 10 SDK is needed for the client half.**

Two things a green build does not prove, both checked by hand:

- `CasinoTab.cs:297` does `AccessTools.Field(typeof(MenuTaskBar), "_toggleButtons")` -- a string,
  not compile-checked. The field dump of `EFT.UI.MenuTaskBar` shows
  `Dictionary<EMenuType, AnimatedToggle> _toggleButtons`, the exact name and generic shape the code
  casts to. It is fine.
- `CasinoTab.cs:1194` does `transform.Find("Hover")` -- a *prefab child name*, which is in an asset
  bundle and cannot be verified from metadata at all. **Unverified.** It degrades safely: `_glow` is
  null-guarded at all three use sites, so a rename costs the hover glow, not a crash.

## The server half: compiles on net9.0, but two real defects were found underneath

All 19 `net10.0` projects retarget to `net9.0` and build against real 4.0.13 metadata, and all
**480 unit tests pass**. **Zero errors were attributable to net10 -> net9** -- the four `.Game`
projects and their tests needed nothing but a TFM string change. Every real error came from the
4.1.2 -> 4.0.13 API delta, and it is overwhelmingly namespace relocation: 4.1 introduced
`Helpers.*` / `Services.*` sub-namespaces that do not exist in 4.0.13. Measured cost of the port:
**441 changed lines across 52 files.**

The mechanical shims, for the record:

| 4.1.2 | 4.0.13 |
| --- | --- |
| `IModMetadata` (interface) | `AbstractModMetadata` (abstract record) |
| `IOnLoad.OnLoadAsync(CancellationToken)` | `IOnLoad.OnLoad()` |
| `RouteAction<T>` 5-arg lambda -> `object` | 4-arg `(url, info, sessionID, output)` -> `ValueTask<string>` |
| `OnLoadOrder` constants | renamed and renumbered; 8 names shared, only `Watermark` shares a value |
| `Services.Commerce.PaymentService` | `Services.PaymentService` |

`OnLoadOrder` is a static class of `int` consts in 4.0.13, not an enum -- which matters, because the
ported code writes `OnLoadOrder.PostSptModLoader + 1`.

### Defect 1 -- the item-event port as first written is dead on arrival

This is the finding that a passing build hid, and it was caught by *executing* the live
`C:\SPT\SPT\SPTarkov.Server.Core.dll` rather than by reading it.

4.0.13 globally registers `BaseInteractionRequestDataConverter`, whose `ConvertToCorrectType` is a
closed switch over EFT's own action strings **with a throwing default**. Run against the real DLL,
`"Move"` deserializes fine, and **all ten of the mod's actions throw**:

```
System.Exception: Unhandled action type BlackjackSync, make sure the
BaseInteractionRequestDataConverter has the deserialization for this action handled.
```

-- same for `PokerSync`, `RouletteSync`, `SlotsSync`, `BlackjackDeal`, `BlackjackPlay`, `PokerSit`,
`PokerDeal`, `PokerAct`, `PokerLeave`. The throw happens inside `JsonUtil.Deserialize`, called from
`StaticRouter`, **before any `ItemEventRouterDefinition` is consulted**. So hand-decoding
`body.ExtensionData` in a ported router can never execute.

The fix is better than the workaround, and it is a supported extension point:

```csharp
BaseInteractionRequestDataConverter.RegisterModDataHandler(
    "BlackjackSync", raw => JsonSerializer.Deserialize<BlackjackSyncAction>(raw));
```

`public static void RegisterModDataHandler(string action, Func<string, BaseInteractionRequestData>)`
exists in 4.0.13 and the converter is registered globally by `SptJsonConverterRegistrator`. So
**4.0.13 keeps the typed action records** -- no `ExtensionData` archaeology. The type does not exist
in 4.1.2 at all; 4.1 replaced it with `ItemRouteAction<T>.BodyType`, which is why a pure
metadata diff misses it.

**And the blast radius is far smaller than it looks.** The shipping clients do not use the
item-event transport for play at all: `PokerApi.cs` posts all six calls to static routes and
`BlackjackApi.cs` does the same. The only item event any client sends is
`ProfileSync.Request("<Table>Sync")`. So `PokerSit/Deal/Act/Leave` and `BlackjackDeal/Play` are
**registered on the server but dead in the shipping client** -- only the four `*Sync` actions need a
handler registered. (`RouletteItemEventRouter.cs`'s class doc, which claims "Poker and Blackjack put
their whole game on the item-event transport", is stale.)

### Defect 2 -- Spectre.Console would break server startup

`src/Casino.Server/Banner.cs` has `using Spectre.Console;` and `Startup.OnLoad()` calls
`Banner.Rainbow(...)`. **SPT 4.0.13 ships no Spectre assembly anywhere** -- a search of all of
`C:\SPT` finds only two unrelated game asset bundles. Adding a `PackageReference` fixes the compile
and nothing else: `Casino.Server.csproj` sets `CopyLocalLockFileAssemblies=false`, and every pack
script uses an explicit allowlist of `*.Server.dll` / `*.Game.dll` / `pdb` / `config.json`. So the
DLL is neither copied nor packaged, and `OnLoad` throws `FileNotFoundException` **at server
startup**. Two assemblies would have to ship, not one (`Spectre.Console` and `Spectre.Console.Ansi`).

Simplest fix: drop the Spectre dependency from `Banner.cs`.

## Load-order: the gate is not what CLAUDE.md says

Two corrections to `CLAUDE.md`, both verified against the live install:

- **`PluginValidator` does not exist in 4.0.13.** It was added in 4.1.3. So the claim that "a plugin
  built against a 4.0 install is rejected outright" has no counterpart on the older line.
- **A rejected mod is loud, not silent, and it takes everything with it.** `ValidateCoreAssemblyReference`
  runs at `ModValidator.cs:24`, *before* the `SptVersion` semver check at line 136. A mod referencing
  `SPTarkov.Server.Core` 4.1.2 on a 4.0.13 server dies on an unhandled throw -- "requires a minimum
  SPT version of `4.1.2`, but you are running `4.0.13`" -- and the `SptVersion` gate is never reached.
  `CLAUDE.md`'s "loads nothing and *logs nothing*" is wrong for this case.

In practice a `net10.0` mod assembly cannot load into 4.0.13's .NET 9 runtime at all, which fails
earlier still.

## Remaining work, honestly scoped

Everything above compiles and unit-tests. **Nothing has been loaded into a running SPT server.** DI
registration, route dispatch, `OnLoad` ordering and the JSON handler path are all unexercised, and
the 480 passing tests cover **none** of the rewritten transport -- no test constructs any
`*ItemEventRouter` or exercises the round-trip.

Still to do for a working 4.0.13 build:

1. Register a `BaseInteractionRequestDataConverter` mod handler for the four `*Sync` actions.
2. Remove Spectre from `Banner.cs`.
3. Port the three parked routers (`Poker`, `Roulette`, `SlotMachine`) -- one was ported, three were
   excluded from the build to get it green.
4. Move `SptVersion` in all five places; only `Casino.Server/ModMetadata.cs` was changed, and the four
   `TableInfo.cs` still say `~4.1.3` (display-only, but the banner would lie).
5. Retarget the four `*.Server.Tests` projects and re-run them.
6. Load it into the actual server and watch it boot.
